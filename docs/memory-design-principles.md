# LifeOS 长程记忆设计原则

> 状态：当前设计基线（2026-10-17）
>
> 本文定义 LifeOS、ai-memory 与 TencentDB Agent Memory 之间的职责边界，以及长程记忆后续设计必须遵守的约束。它是设计原则，不等同于所有能力已经完成生产验收。

## 总体架构判断

**TencentDB 是全局长期认知的目标后端；ai-memory 是项目级连续性后端；LifeOS 是二者之间的审核、隔离、晋升和编排层。项目记忆只有经过显式提炼和授权，才可以进入全局认知。**

三者不保存同一份 active 记忆作为长期双重权威：

- **LifeOS** 管理入口、来源、候选、用户审批、scope、纠错、撤回、跨后端引用和任务级组合。
- **ai-memory** 管理单个项目的工作连续性，包括项目背景、决策、进展、阻塞、执行记录、Wiki、handoff 和项目内上下文。
- **TencentDB Agent Memory** 管理经过审核的长期认知：L1 原子记忆，以及基于可追溯 L1 生成的 L2 场景记忆和 L3 全局画像。
- **原始来源** 保留完整证据；它可以被回读和审计，但不直接等同于长期记忆。

迁移完成前，LifeOS 本地 store 是运行时权威；外部后端只做受控同步或召回，不开启长期双写。

## 不可违反的原则

1. **入口归 LifeOS。** 任何外部来源进入长期认知前，都必须经过 LifeOS 的候选流程、来源记录和用户可理解的审核入口。
2. **来源优先。** 每条候选、L1、L2、L3 派生结果都必须能追溯到来源记录、来源版本、scope、生成/晋升理由和必要的审批引用。
3. **职责分离。** ai-memory 不替代用户全局画像；TencentDB 不替代项目 Wiki/handoff；LifeOS 不复制两者的全部内容来形成第三套权威。
4. **项目默认隔离。** 项目记忆按用户和项目隔离。不同项目、不同用户或不同场景不能因为文本相似而自动互相召回。
5. **禁止自动跨层晋升。** 项目记忆不能自动晋升为场景记忆或全局记忆。晋升必须有明确提炼结果、目标 scope、晋升理由和用户授权。
6. **原始证据不直接充当长期记忆。** 对话、日志、Wiki、handoff、计划和复盘先作为证据保存；只有稳定、可复用、边界清楚的认知才进入候选和 L1。
7. **派生画像不是新证据。** L2/L3 是从已审核 L1 派生的视图，不能脱离 L1 单独成为不可解释的事实来源。
8. **纠错必须可追溯。** 更正应创建带来源的新版本，并将旧版本标记为 superseded；不能静默覆盖历史内容。
9. **撤回必须沿来源链生效。** 用户撤回或删除授权后，相关 L1、派生画像、检索索引和缓存都必须停止影响后续回答；原始来源是否删除按其独立保留规则处理。
10. **过期必须可表达。** 记忆需要支持有效期、最近确认时间或衰减状态。过期记忆不能继续以 active 事实参与画像和召回，但应保留审计关系。
11. **故障安全。** 外部后端不可用、身份映射缺失、scope 不明确或 provenance 不完整时，系统降级到安全的本地结果或不召回，不能回退到全局记忆。
12. **最小上下文。** 每次任务只注入当前任务需要的少量相关记忆；长文、原始记录和项目页面按需回读，不直接塞入上下文。

## 长程记忆的分层模型

```text
L0 原始证据
  LifeOS 对话/计划/复盘/反馈、Agent 执行记录、ai-memory 项目页面
        ↓ 提炼、去重、范围判断、用户审核
LifeOS 候选与审核账本
        ↓ 显式授权和晋升
L1 原子记忆（TencentDB）
        ↓ 受控聚合，保留 generation refs
L2 场景记忆 / L3 全局画像（TencentDB）
        ↓ 按任务 scope 受控召回
本轮 Memory Context
```

L0 解决“发生过什么”，L1 解决“确认了什么稳定事实”，L2/L3 解决“在某个场景或全局上如何组织这些事实”。三层都要保留向下的来源关系。

## 需要继续讨论的三个问题

### 1. 长程记忆保存什么

候选进入 L1 前，至少回答：

- 这是不是跨时间仍可能有用的事实、偏好、决策或方法？
- 它适用的 scope 是全局、场景还是项目？
- 它的证据是什么，最近何时被确认？
- 它与已有记忆是补充、冲突、修正还是重复？
- 它失效的条件是什么？

不满足这些条件的内容留在 L0 或 ai-memory 项目层，不进入全局长期认知。

### 2. 记忆如何检索

检索应分成四步，而不是一次向量搜索：

1. **范围过滤**：先按 user、project、scenario、status、有效期和 allowlist 过滤。
2. **来源分路**：项目任务优先召回 ai-memory；长期认知召回 TencentDB；原始证据只在需要核实时回读。
3. **相关性排序**：结合关键词、语义相似度、最近确认时间、置信度、任务类型和记忆稳定性排序。
4. **上下文预算**：按类别和来源设置数量/字符预算，保留 provenance；超出预算时优先保留稳定且直接相关的 L1，压缩或延后读取其余内容。

当前本地检索器仍是字面匹配；后续可以增加 embedding，但 embedding 只能改善排序，不能绕过 scope、状态和来源权限过滤。

### 3. 记忆如何压缩

压缩不是简单截断文本，而是保留认知结构：

- **原始记录压缩**：保留原文和索引，生成短摘要作为可选入口；摘要必须能回指原文。
- **项目记忆压缩**：把多个执行事件整理为项目状态、关键决策、当前阻塞、下一步和 handoff；不把临时日志直接升级为全局事实。
- **L1 合并**：只合并同一 scope、同一语义且来源兼容的原子记忆；保留被合并条目、证据集合和版本关系。
- **L2/L3 聚合**：由已审核 L1 生成场景/画像视图；任何冲突都保留冲突来源，不用无来源的总结覆盖它们。
- **过期与降权**：过期、低置信度或很少被确认的记忆可以降权或移出 active，但不能在没有审计记录的情况下物理消失。

压缩后的结果必须满足：更短、可追溯、scope 不变、能够被纠正和撤回，并且不会制造原始来源中不存在的新事实。

## 后续实现顺序

1. 先统一 `MemoryRecord` 的 provenance、确认时间、有效时间、版本关系和晋升关系字段。
2. 再实现 scope-first 的多路检索接口和统一结果格式。
3. 然后实现项目记忆到候选的显式晋升流程，不做自动跨项目晋升。
4. 最后实现 L1 合并、L2/L3 聚合和可回溯压缩，并用固定查询集评估召回正确性、隔离性、来源完整率和上下文长度。
