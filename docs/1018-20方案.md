# LifeOS 长程记忆方案（10/18–10/20）

> 状态：供讨论的实施方案草案
> 日期：2026-10-18
> 目标：先建立可复现的长程记忆评测，再并行改进检索召回与可追溯压缩；图能力放在最后，根据评测缺口决定是否投入。

## 最终目的

让 LifeOS 在任务开始时能从正确的记忆层取回少量、相关、仍有效且来源清楚的上下文；能区分当前事实与历史事实；记忆冲突、纠错或撤回后不继续使用旧结论；证据不足时明确表示不知道或请求澄清。

这是一个可测量的记忆工程目标，不承诺 Agent 记住全部经历、自动形成完整人格，或因此保证所有回答正确。衡量改进要看答案质量、证据召回、scope 隔离、来源完整性、上下文 token 与查询延迟，而不能只看“记住了多少”。

## 已有架构和本轮边界

- LifeOS 管理入口、来源、候选审批、scope、纠错/撤回、跨层晋升和任务级编排。
- ai-memory 负责单项目连续性，例如项目背景、决策、执行结果、Wiki 和 handoff。
- TencentDB Agent Memory 是已审核全局长期认知的目标后端；L2/L3 画像应能追溯到批准的原子记忆。
- 原始对话、执行轨迹和文档是证据，不直接等于全局长期记忆；项目记忆不会自动晋升。
- 当前 LifeOS 本地检索以 scope/status 过滤后做词面和模糊匹配；ai-memory 适配器目前是显式项目 scope 下的有界只读查询。尚无统一的关键词/语义/结构化多路召回与证据排序流程。
- MemoryRecord v4 已开始补 provenance revision、确认时间、有效期、版本关系和晋升元数据。此方案不把字段扩展等同于晋升功能或跨后端生命周期已经完成。

本轮先建立基准、数据适配和方案；压缩与检索可以并行做小步原型。暂不切换记忆权威、不启用自动跨层晋升、不引入图数据库，也不把整个原始对话塞进每轮上下文。

### 指标

- **回答质量**：按题型统计官方 evaluator 的 answer accuracy；拒答题单独统计正确拒答率和错误作答率。不同 judge 或 prompt 的结果不直接横比。
- **证据召回**：session/turn 或 MemoryRecord 粒度的 Recall@K、NDCG@K；同时观察多证据题的 all-evidence recall，避免只命中部分证据就算成功。
- **治理正确性**：跨 scope 泄漏次数必须为 0；已撤回、已过期或被 supersede 的事实不应作为当前答案证据；所有答案证据 provenance 覆盖率为 100%。
- **效率**：记录输入上下文 token 数、检索延迟和压缩/抽取成本。先建基线，依据实际结果设阶段改进门槛，不先承诺任意百分比。

LongMemEval 官方 retrieval 指标不会把不可回答题当作普通 recall 题，因此必须独立测 abstention。所有数据切片、输出和 judge 版本需保留，确保压缩或检索前后可重跑比较。

## 工作流 A：检索与召回详细方案

目标是把当前“词面模糊匹配”演进成 scope-first、多路召回、证据可追溯的检索流水线。先在现有 provider 之上建立接口和评测，不先更换后端。

### 在线检索步骤

1. **解析查询意图**：识别项目/任务 ID、用户/场景、时间范围、实体、查询类型（当前状态、历史事实、偏好、项目续接、操作经验、总结或无答案）。任务执行上下文中的 project ID 是可信 scope 输入；LLM 分类只能提出意图，不能扩大授权范围。
2. **确定查询范围**：在检索前确定可访问的 user、project、scenario、source 和状态白名单。项目执行先查对应 ai-memory 项目；全局长期认知查 TencentDB 中已批准并仍 active 的记忆。只有用户明确提出跨域问题且产品策略允许时才并查多个已授权 scope。任何 provider 超时、身份映射不完整或 scope 不明确均 fail closed，不降级为全局搜索。
3. **硬过滤**：过滤 user/project/scope、active 状态、确认状态、撤回/过期状态、有效期和本地 active-ID allowlist。时间问题使用 `valid_from`/`valid_until` 或 as-of 时间；`created_at` 只能代表录入时间，不能替代事实有效时间。硬过滤先于排序，不能靠低排名弥补越权候选。
4. **并行多路召回**：从允许的候选集中分别做关键词/BM25、语义向量、结构字段（实体、category、source_ref、时间）召回；当前已有的 fuzzy/local 路径作为 lexical baseline。项目 ai-memory 的 Wiki/handoff 命中作为项目证据召回；它不是批准的全局 MemoryRecord。
5. **融合与排序**：先用 Reciprocal Rank Fusion 等不依赖可比原始分数的方式合并各路 top-N；然后用可解释特征轻量重排：语义相似、关键词覆盖、实体匹配、时间匹配、scope 精确度、confidence/source quality、有效性和必要的 recency。明确的时间意图优先于单纯“最近录入”。后续有评测证据再考虑 cross-encoder/LLM reranker。
6. **去重与版本收敛**：同一来源/相同语义的重复结果合并展示但保留所有 source refs；同一 `version_of` 链仅将当前有效版本作为“当前事实”，历史问题按时间选择对应版本。无法判定新旧或内容冲突时并列返回并标注冲突，不做平均或静默覆盖。
7. **构建有预算的 evidence pack**：按任务类别限额，先放最相关的少量 L1 和记忆直接证据；稳定的 L2/L3 或项目摘要可做导航/背景，不能替代其引用的原始 MemoryRecord。返回 record ID、scope、来源/修订、有效期、确认时间、命中原因和分数，超预算时压缩展示或延迟读取来源详情，不抹掉追溯信息。
8. **回答与拒答**：回答必须基于 evidence pack；对冲突说明有效时间和来源差异。无证据、低置信或召回失败时 abstain 或请求澄清，不用其他项目、unassigned 数据或过期旧版本填空。

### 缓存、故障与接口边界

- 缓存 key 至少包含规范化 query、user/project/scenario、as-of 时间、provider 和 lifecycle/index/view generation。提交、纠错、撤回、到期、身份映射或授权变更必须失效相关缓存。
- TencentDB 和 ai-memory 的候选结果保留 provider 及来源链接；统一 evidence DTO 只做查询结果，不把 ai-memory 页面自动变成全局 MemoryRecord。
- provider 不可用时，只可回退到仍满足同一 scope 的本地结果；没有安全候选则明确返回空。任何错误都不能触发宽 scope 查询。
- 首轮先做 deterministic lexical + metadata/temporal filters + provider 结果融合；向量召回与更复杂重排按离线评测缺口逐步加入。

### 检索验收

- 全部 governance mini-set 的跨 scope 泄漏为 0；撤回、过期和 superseded 旧版本不作为当前事实召回。
- 证据引用完整率 100%；provider 故障时不扩大检索范围。
- 在相同数据集/模型/judge 下，对比 baseline 的 answer accuracy、Recall@K、all-evidence recall、拒答错误率、上下文 token 和延迟；至少不以明显损害隐私/来源完整性的方式换取召回率。

## 工作流 B：压缩与派生视图详细方案

压缩结果建模为**可重建的派生视图**，而不是新的权威 MemoryRecord。L1 原子记忆仍是经 LifeOS 审核的事实单位。压缩可以与检索工作并行，双方共享 scope、active/valid 状态和 provenance 规则。

### 压缩层次

- **L0 证据导航摘要**：对长对话/执行记录生成可选短摘要和目录，原文照常保留。摘要逐段附 source ID、revision、时间范围，只做检索入口，不晋升为认知事实。
- **项目连续性摘要**：ai-memory 维护项目背景、决策、进度、阻塞、下一步和 handoff。按项目隔离，不自动复制到全局。
- **TencentDB L2/L3 派生视图**：仅从 LifeOS 已批准、active、scope 适配的 L1 生成场景摘要和全局画像。若后端不能保存 claim 级来源清单，LifeOS 保留 generation manifest 与来源映射。

### 派生数据形状

建议的独立派生对象 `DerivedMemoryView` 至少包含：`view_id`、`view_type`、scope、`generation_id`、`status`（active/dirty/stale）、逐条 `claims`、lineage 和 token 数。每条可独立验证的 claim 至少记录：`claim_id`、文本/类型、可选 semantic key、scope、source MemoryRecord IDs 与 revision、有效时间区间、状态、confidence/依据、support count、冲突组、`derived_at`、生成器与 prompt/schema 版本。一次生成还要记录输入 watermark/source hash、上游 view IDs 和 schema 版本。若 TencentDB 现有 L2/L3 不能逐 claim 保存引用，LifeOS 保留 generation manifest 与来源映射。摘要要能定位来源并重建；不能只留一段无引用的自然语言。

新概括如果超出来源记录能够直接支持的范围，例如由多条局部偏好推断出稳定人格，应转为 LifeOS 候选走审核，不能静默写入画像。重复出现次数可保留为支持信息，但不能直接当作 confidence。

### 增量更新和冲突规则

1. MemoryRecord 被确认、纠正、撤回或过期时，立即更新其在线 eligibility，并依据 source → claim → L2 → L3 的依赖关系，把受影响的 view 标成 dirty。
2. 后台将相同 scope/主题的变更 debounce 合并，以幂等任务增量重算；输入集合 hash 未变时不调用模型。简单格式整理和重复检测优先 deterministic，模型只用于需要语义归纳的步骤。
3. 新 generation 生成后校验 scope、来源和有效期，再原子切换 active pointer；旧 generation 保留审计但不继续提供已失效的 claim。
4. 撤回、过期和 supersede 必须先从在线召回资格中生效，再异步重建摘要。重建失败可回退到仍有效的 L1 查询，不可回退到失效旧摘要。
5. 相同 scope、含义相同且来源兼容的内容可以合并为 claim，但必须保留全部支持来源。相互矛盾的内容并列保留其时间、版本和来源；不能平均、隐藏冲突或让新摘要覆盖历史证据。
6. 摘要/画像缺失或 dirty 时，在线检索退回合格的原子记忆，不等待压缩任务；同样不扩大 scope。

### 压缩验收

- 摘要 claim 来源可解析率 100%；派生 view 不增加没有来源支持的新事实。
- source 被纠正/撤回/过期后，下一次在线检索不返回依赖它的旧 claim；缓存和索引同步失效。
- 重复合并不丢 provenance；冲突保留并可解释；任意 view 能从当前有效的上游 MemoryRecord 重建。
- 在相同 benchmark 上，记录压缩前后的 token 数、答案准确率、支持证据覆盖率与构建成本。目标是节省上下文，同时不降低答案被证据支持的程度；达不到就不启用该压缩视图。

## 后续顺序

1. 完成 benchmark adapter 和基线，确认哪些类型主要是提取、召回、时间理解、压缩还是拒答的问题。
2. 根据失败案例并行实现检索切片与派生压缩切片；以同一题集分别做检索消融和上下文压缩消融。
3. 验证纠错/撤回/过期在缓存、派生视图与外部 provider 召回上的传播。
4. **最后评估图能力**：只有在多跳实体关系/时间问答持续失败，且 lexical+dense+temporal+metadata 方案不足时，才做 Graphiti 式图检索原型。用同一 benchmark 比较收益、延迟、成本、部署复杂度和 provenance 覆盖；未证明收益前不引入新的图数据库。

## 图能力的启动条件

至少满足以下条件后才进入图能力原型：已建立稳定基线；已完成 scope-first 和混合检索；失败集中在实体关系多跳、关系路径或复杂时间状态，而非输入提炼错误、source 缺失或权限过滤问题；能够在原子事实与图边之间保留可撤回的来源链。若结果只是让答案更长、成本更高而未改善证据支持率，就不采用。

## BM25 与历史检索阶段结果（2026-10-19）

LongMemEval-S 的 500 题离线评测中，BM25 的 Recall@5、全证据召回率、MRR、NDCG@5 分别为 0.879、0.832、0.910、0.883；legacy 分别为 0.762、0.681、0.765、0.721，hybrid 分别为 0.761、0.679、0.765、0.720。该结果支持把 BM25 作为可选检索策略继续评估，不足以证明它适合取代 LifeOS 默认 hybrid。

LifeOS 治理集上，BM25 的原始证据 Recall@5 为 1.000，hybrid 为 0.923；两者当前有效证据 Recall@5 均为 0.846，且 forbidden candidate 与跨 scope 违规均为 0。历史样例 gov-002 经修正后，hybrid 和 BM25 都能在保留同一会话话题时召回 m-201，并排除后续版本 m-208。历史查询使用 0.20 的最低相关度门槛；不能据单个历史样例推断整体历史检索质量。
